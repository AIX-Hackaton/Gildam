# 길담 Product Specification

> 이 문서는 Codex를 포함한 모든 개발 참여자가 길담의 기획 의도, MVP 범위, 화면 동작, 디자인 원칙을 동일하게 이해하기 위한 기준 문서다.  
> 구현 전에 이 문서를 먼저 읽고, 문서와 충돌하는 임의의 기능 추가나 해석은 하지 않는다.

---

## 0. 문서 사용 원칙

- 이 문서는 현재 MVP의 기준이다.
- 기획이 변경되면 코드보다 먼저 이 문서를 수정한다.
- 명시되지 않은 기능은 임의로 추가하지 않는다.
- 화면을 구현할 때는 기능뿐 아니라 문제 해결 의도와 사용자 경험을 함께 지킨다.
- 불명확한 부분은 추측해서 구현하지 말고 질문하거나 `TODO`로 남긴다.

---

# 1. 프로젝트 개요

## 1.1 프로젝트명

**길담**

### 서비스 한 문장

> 차 없이 전남을 다녀올 수 있을지를 먼저 판단하고, 그 하루를 지역 경험과 기록으로 연결하는 AI 문화관광 큐레이터

## 1.2 이름의 의미

‘길담’은 다음 두 가지 의미를 가진다.

- 지역의 길을 담는다.
- 여행자가 그곳에서 보낸 하루를 기록으로 남긴다.

MVP는 광주 출발 전남 당일치기 여행을 대상으로 하지만, 향후 다른 지역의 문화관광 데이터와 코스를 추가해 전국 단위 서비스로 확장할 수 있다.

## 1.3 프로젝트 목적

광주·전남에는 관광지, 지역 음식, 문화시설과 로컬 콘텐츠가 충분히 존재한다. 그러나 자가용이 없는 여행자는 관광 정보를 찾은 뒤에도 다음 내용을 직접 확인해야 한다.

- 광주에서 실제로 당일치기가 가능한가
- 대중교통 환승이 과도하지 않은가
- 도보 이동이 감당 가능한가
- 주어진 시간 안에 귀가할 수 있는가
- 코스 안에서 어떤 지역 음식과 문화를 경험할 수 있는가
- 여행 중 무엇을 관찰하고 기록하면 좋은가

길담은 흩어진 관광 정보와 이동 조건을 하나의 코스로 연결해, 사용자가 **실제로 떠날 수 있는 여행을 빠르게 선택하도록 돕는 것**을 목적으로 한다.

# 2. 문제 정의

## 2.1 핵심 문제

> 관광지가 부족한 것이 아니라, 자가용 없이 주어진 시간 안에 실제로 완주 가능한 여행인지 판단하기 어렵다.

기존 서비스에서는 관광지 정보, 길찾기, 일정, 후기와 여행 기록이 분리되어 있다. 사용자는 여러 서비스를 오가며 정보를 직접 비교하고 코스를 조립해야 한다.

## 2.2 해결하려는 사용자 불편

1. 갈 곳은 많지만 내 출발지와 시간에 맞는지 판단하기 어렵다.
2. 환승 횟수, 도보 시간, 총 이동시간과 귀가 가능성을 직접 계산해야 한다.
3. 관광지와 지역 음식을 하나의 동선으로 연결하기 어렵다.
4. 장소를 방문해도 무엇을 알고 보고, 무엇을 기록하면 좋은지 알기 어렵다.
5. 추천 결과를 본 뒤 다시 지도 앱에서 장소를 검색해야 한다.

## 2.3 해결하지 않는 문제

현재 MVP는 다음 문제를 해결하지 않는다.

- 전남 전체 지역의 실시간 자동 코스 생성
- 실시간 버스 지연과 막차 정보의 완전한 연동
- 숙소, 예약, 결제, 리뷰
- 맛집 순위와 사용자 평점
- 로그인과 개인 기록 보관
- 현재 위치 기반 실시간 재추천
- 전체 여행 사진 분석
- 여행 커뮤니티 기능

# 3. 목표 사용자

## 3.1 핵심 타겟

광주·전남을 잘 모르고, 자가용 없이 광주에서 전남 당일치기 여행을 떠나려는 20~30대 자유여행자

## 3.2 사용자 특성

- 광주송정역 또는 유스퀘어에서 출발한다.
- 혼자, 친구 또는 연인과 당일치기 여행을 떠난다.
- 여행 자체에는 관심이 있지만 계획 과정에는 피로를 느낀다.
- 모바일 지도와 SNS 사용에 익숙하다.
- 자연, 산책, 역사, 문화, 지역 음식과 사진 기록에 관심이 있다.
- 많은 선택지보다 적은 수의 신뢰할 수 있는 추천을 선호한다.
- 별도 앱 설치나 복잡한 입력 과정은 부담스럽게 느낀다.

## 3.3 대표 사용자 시나리오

광주송정역에서 오전에 출발할 수 있는 사용자가 자연·산책과 감성기록 취향을 선택한다. 길담은 시간과 이동 조건을 충족하지 못하는 코스를 제외하고 담양 느린 산책 코스를 1순위로 추천한다.

사용자는 다음 정보를 확인하고 여행 여부를 판단한다.

- 예상 소요시간
- 총 도보시간
- 환승 횟수
- 이동 피로도
- 추천 이유
- 지역 음식
- 주요 장소
- 로컬 포인트
- 오늘 담아볼 장면

이후 지도 앱을 통해 실제 길찾기로 이동한다.

# 4. 제품 목표와 성공 기준

## 4.1 제품 목표

### Goal 1. 계획 부담 감소

사용자가 여러 플랫폼을 오가지 않고 짧은 입력만으로 코스를 선택할 수 있어야 한다.

### Goal 2. 실행 가능성 판단 지원

추천 결과에서 도보, 환승, 소요시간과 이동 피로도가 먼저 보여야 한다.

### Goal 3. 추천 신뢰성 확보

검증된 코스 데이터 안에서만 추천하고 추천 이유를 설명해야 한다.

### Goal 4. 지역 경험 연결

관광지뿐 아니라 지역 음식과 로컬 포인트를 하나의 코스 안에서 제공해야 한다.

### Goal 5. 여행 기록으로의 확장

현재 구현 범위에서는 상세 화면에 ‘오늘 담아볼 장면’을 제공한다. 장면 카드 생성은 후속 범위다.

## 4.2 MVP 성공 기준

- 사용자가 조건 입력부터 추천 확인까지 2분 이내에 완료할 수 있다.
- 추천 결과에서 이동 피로도와 실제 이동 수치를 바로 확인할 수 있다.
- 정상 결과, 결과 없음, 로딩, 오류 상태가 모두 구현되어 있다.
- 320px 이상의 모바일 화면에서 가로 스크롤이 발생하지 않는다.
- 키보드만으로 핵심 흐름을 이용할 수 있다.
- 컴포넌트에 특정 코스 데이터가 하드코딩되어 있지 않다.
- mock data를 실제 API로 교체해도 화면 구조를 크게 수정하지 않아야 한다.

# 5. 현재 MVP 구현 범위

## 5.1 필수 화면

1. 홈
2. 조건 입력
3. 추천 결과
4. 코스 상세
5. 결과 없음
6. 로딩 상태
7. 오류 상태

## 5.2 데이터 범위

- 출발지: 광주송정역, 유스퀘어
- 가능 시간: 6시간, 하루 종일
- 취향:
  - 자연·산책
  - 역사·문화
  - 음식·시장
  - 감성기록
- 대상 지역:
  - 담양
  - 나주
  - 목포
- 코스 수: 총 6개
  - 지역별 저피로 코스 1개
  - 지역별 일반 코스 1개

## 5.3 현재 단계에서 제외하는 화면

- 로그인
- 마이페이지
- 저장한 여행
- 전체 지도 탐색
- 사진 업로드
- 오늘의 장면 카드 생성
- 리뷰와 평점
- 예약과 결제
- 관리자 페이지

# 6. 핵심 사용자 흐름

## 6.1 정상 흐름

```text
홈
→ 여행 조건 입력
→ 추천 결과
→ 코스 상세
→ 외부 지도에서 장소 보기 또는 길찾기
```

## 6.2 결과 없음 흐름

```text
여행 조건 입력
→ 조건에 맞는 코스 없음
→ 결과 없음 안내
→ 조건 다시 설정
```

## 6.3 오류 흐름

```text
추천 요청
→ 데이터를 불러오지 못함
→ 오류 안내
→ 다시 시도
```

# 7. 화면별 요구사항

## 7.1 홈

### 목적

서비스의 핵심 가치를 짧게 전달하고 조건 입력으로 이동시킨다.

### 핵심 메시지

> 차 없이도 충분한 전남 당일치기 여행  
> 출발지와 시간, 취향을 선택하면 실제로 다녀올 수 있는 코스를 추천해드려요.

### 필수 요소

- 길담 로고 또는 서비스명
- 핵심 카피
- 짧은 설명
- 대표 이미지 또는 일러스트
- `내 여행 조건 입력하기` CTA

### 동작

- CTA 선택 시 조건 입력 화면으로 이동한다.

### 완료 조건

- 첫 화면만 보고 서비스 목적을 이해할 수 있다.
- CTA가 가장 강한 시각적 위계를 가진다.
- 모바일 첫 화면에서 핵심 카피와 CTA를 확인할 수 있다.

---

## 7.2 조건 입력

### 목적

사용자가 최소한의 선택으로 추천 조건을 완성한다.

### 입력 항목

#### 출발지

단일 선택

- 광주송정역
- 유스퀘어

#### 가능 시간

단일 선택

- 6시간
- 하루 종일

#### 취향

복수 선택

- 자연·산책
- 역사·문화
- 음식·시장
- 감성기록

### 동작 규칙

- 출발지와 가능 시간은 하나만 선택할 수 있다.
- 취향은 한 개 이상 복수 선택할 수 있다.
- 필수 조건이 완료되기 전까지 `코스 추천받기` 버튼을 비활성화한다.
- 뒤로 갔다가 돌아와도 선택값을 유지한다.
- 제출 중에는 중복 클릭을 방지한다.

### 상태

- 초기 상태
- 선택 상태
- 버튼 비활성화
- 버튼 활성화
- 제출 중 로딩

### 완료 조건

- 선택 여부가 색상만으로 구분되지 않는다.
- 체크 아이콘, 테두리 또는 텍스트 상태를 함께 사용한다.
- 버튼과 선택 항목은 키보드로 조작할 수 있다.

---

## 7.3 추천 결과

### 목적

사용자가 추천 코스를 빠르게 비교하고 추천 이유를 납득하도록 한다.

### 필수 요소

- 입력 조건 요약
- `조건 변경` 버튼
- 1순위 추천 코스
- 대안 코스 1~2개
- 코스 카드

### 코스 카드에 포함할 정보

- 코스명
- 지역
- 대표 이미지
- 취향 태그
- 이동 피로도
- 예상 소요시간
- 총 도보시간
- 환승 횟수
- 추천 이유 2~3개
- `코스 자세히 보기` 버튼

### 위계

1순위 추천 카드는 대안 코스보다 시각적으로 명확하게 강조한다.

### 상태

- 정상 결과
- 결과 1개
- 결과 여러 개
- 로딩
- 결과 없음
- 오류

### 완료 조건

- 카드 상단에서 이동 피로도와 이동 정보를 빠르게 확인할 수 있다.
- 추천 이유가 단순 점수가 아니라 문장으로 제공된다.
- 코스 선택 시 상세 화면으로 이동한다.

---

## 7.4 코스 상세

### 목적

사용자가 이 코스를 실제로 선택할지 최종 판단하도록 돕는다.

### 정보 순서

1. 코스명과 대표 이미지
2. 핵심 태그
3. 이동 피로도
4. 예상 소요시간, 총 도보시간, 환승 횟수
5. 추천 이유
6. 코스 순서
7. 지역 음식
8. 로컬 포인트
9. 오늘 담아볼 장면
10. 지도 보기 또는 길찾기 CTA

### 코스 순서

타임라인 형태로 보여준다.

예시:

```text
광주송정역 출발
→ 관방제림
→ 메타세쿼이아길
→ 담양 국수거리
→ 골목 산책
```

각 항목에는 필요에 따라 다음 정보를 표시한다.

- 장소명
- 장소 유형
- 머무는 시간
- 이동시간
- 짧은 설명

### 오늘 담아볼 장면 예시

- 전남에서 내가 먹은 음식은?
- 오래된 간판이나 골목의 색감
- 걷다가 발견한 풍경

### 지도 연결

- 현재 MVP에서는 외부 지도 URL을 연다.
- 지도 기능을 앱 안에서 직접 구현하지 않는다.

### 완료 조건

- 모든 내용은 course data를 통해 렌더링한다.
- 상세 컴포넌트 내부에 담양, 나주, 목포 데이터를 직접 하드코딩하지 않는다.
- 하단 CTA가 콘텐츠를 가리지 않는다.

---

## 7.5 결과 없음

### 목적

사용자를 막다른 화면에 두지 않고 다음 행동을 안내한다.

### 메시지 예시

> 조건에 맞는 코스를 찾지 못했어요.  
> 입력한 시간과 이동 조건을 모두 만족하는 검증된 코스가 아직 없습니다.

### 제안할 대안

- 가능한 시간을 하루 종일로 변경하기
- 다른 출발지 선택하기
- 취향 조건을 줄이기

### 필수 CTA

- 조건 다시 설정하기
- 홈으로 돌아가기

### 원칙

- 사용자의 잘못처럼 표현하지 않는다.
- 존재하지 않는 코스를 억지로 추천하지 않는다.
- 결과가 없는 이유를 짧게 설명한다.

---

## 7.6 로딩

### 적용 위치

- 추천 결과 계산
- 코스 상세 불러오기

### 요구사항

- 레이아웃이 크게 움직이지 않도록 skeleton을 사용한다.
- 로딩 중 제출 버튼 중복 클릭을 방지한다.
- 지나치게 긴 애니메이션은 사용하지 않는다.

> 코스를 불러오지 못했어요.  
> 잠시 후 다시 시도해주세요.

### 필수 CTA

- 다시 시도
- 조건 입력으로 돌아가기

### 원칙

결과 없음과 시스템 오류를 구분한다.

# 8. 추천 및 데이터 원칙

## 8.1 추천 원칙

- AI가 새로운 코스를 자유롭게 생성하지 않는다.
- 사전에 등록되고 검증된 코스 DB 안에서만 추천한다.
- 시간 조건을 초과하는 코스는 먼저 제외한다.
- 이동 부담이 지나치게 큰 코스는 제외하거나 추천 순위를 낮춘다.
- 사용자에게 너무 많은 결과를 보여주지 않는다.
- 1순위 추천과 소수의 대안만 제공한다.

## 8.2 이동 피로도

이동 피로도는 다음 값을 기준으로 계산한다.

- 총 도보시간
- 환승 횟수
- 왕복 포함 총 이동시간

초기 기준 예시:

| 항목 | 낮은 부담 | 중간 부담 | 높은 부담 |
|---|---|---|---|
| 총 도보시간 | 15분 이하 | 15~35분 | 35분 초과 |
| 환승 횟수 | 0회 | 1회 | 2회 이상 |
| 왕복 총 이동시간 | 90분 이하 | 90~180분 | 180분 초과 |

UI에서는 피로도 등급만 보여주지 않고 실제 수치도 함께 표시한다.

## 8.3 추천 이유 예시

- 자연·산책 취향과 주요 장소가 잘 맞아요.
- 환승이 1회로 비교적 단순해요.
- 코스 안에서 지역 음식을 경험할 수 있어요.
- 사진으로 남기기 좋은 골목과 자연 요소가 포함되어 있어요.

# 9. Mock Data와 API 계약

## 9.1 개발 순서

현재는 mock data로 먼저 구현한다. 화면 컴포넌트가 mock data를 직접 import하지 않도록 service layer를 둔다.

```text
UI Component
→ Recommendation Service
→ 현재: Mock Data
→ 이후: 실제 API
```

## 9.2 데이터 타입 예시

```ts
type FatigueLevel = "LOW" | "MEDIUM" | "HIGH";

interface TravelConditions {
  departure: "GWANGJU_SONGJEONG" | "USQUARE";
  duration: "SIX_HOURS" | "FULL_DAY";
  preferences: Array<
    "NATURE_WALK" |
    "HISTORY_CULTURE" |
    "FOOD_MARKET" |
    "MEMORY"
  >;
}

interface Course {
  id: string;
  title: string;
  region: string;
  thumbnailUrl: string;
  description: string;
  tags: string[];

  departure: string;
  durationMinutes: number;
  walkingMinutes: number;
  transferCount: number;
  fatigueLevel: FatigueLevel;

  recommendationReasons: string[];

  itinerary: Array<{
    id: string;
    name: string;
    type: "transport" | "place" | "food";
    stayMinutes?: number;
    transportMinutes?: number;
    description?: string;
  }>;

  localFood: Array<{
    name: string;
    description: string;
    imageUrl?: string;
  }>;

  localPoints: Array<{
    title: string;
    description: string;
  }>;

  scenePrompts: string[];
  mapUrl: string;
}
```

## 9.3 구현 원칙

- UI 컴포넌트에서 특정 코스 데이터를 하드코딩하지 않는다.
- 데이터가 일부 누락되어도 화면 전체가 깨지지 않도록 처리한다.
- API 연결 함수는 별도 파일에서 관리한다.
- mock과 실제 API는 동일한 타입을 반환해야 한다.

# 10. UX 원칙

## 10.1 핵심 원칙

### 선택을 줄인다

사용자는 여행 계획에 피로를 느끼는 사람이다. 자유 입력보다 명확한 버튼 선택을 우선한다.

### 이동 가능성을 먼저 보여준다

감성적인 이미지보다 이동 피로도, 도보, 환승, 총 소요시간이 먼저 이해되어야 한다.

### 이유를 설명한다

추천 점수만 보여주지 않고 왜 이 코스가 추천되었는지 문장으로 설명한다.

### 다음 행동을 명확히 한다

모든 화면에는 사용자가 다음에 무엇을 해야 하는지 분명한 CTA가 있어야 한다.

### 기록은 여행 선택을 방해하지 않는다

‘오늘 담아볼 장면’은 서비스의 차별 요소지만, 코스 선택과 이동 정보보다 먼저 강조하지 않는다.

# 11. UI 및 비주얼 방향

## 11.1 레퍼런스 방향

Tripadvisor의 다음 특징을 참고한다.

- 둥근 카드
- pill 형태의 선택 버튼
- 명확한 CTA
- 큰 이미지와 간결한 정보 구성
- 친근하지만 과하게 장식적이지 않은 화면

단, Tripadvisor를 복제하지 않고 길담의 정보 구조와 브랜드에 맞게 재해석한다.

## 11.2 전체 분위기

- 정보는 명확하게
- 선택은 간단하게
- 기록 영역은 조금 더 감성적으로
- 관광 홍보물처럼 복잡하게 만들지 않는다
- 지나친 그라데이션과 장식은 피한다

## 11.3 형태

- 주요 카드와 버튼은 둥근 모서리를 사용한다.
- 선택 UI는 pill 또는 rounded button을 사용한다.
- 카드 안의 정보 계층을 명확히 구분한다.
- 한 화면에 너무 많은 카드와 태그를 배치하지 않는다.

## 11.4 문체

- 짧고 친절한 존댓말
- 과도한 감성 문구 금지
- 행정기관식 표현 최소화
- AI가 모든 것을 결정하는 것처럼 표현하지 않는다.

좋은 예:

- 내 조건에 맞는 코스를 찾았어요.
- 환승이 1회로 비교적 단순해요.
- 조건에 맞는 코스를 찾지 못했어요.

피해야 할 예:

- AI가 완벽한 여행을 설계해드려요.
- 당신만을 위한 환상적인 전남 여행
- 최적의 여행 경험을 선사합니다.

# 12. 반응형 원칙

## 12.1 기준

- 모바일 퍼스트
- 최소 지원 폭: 320px
- 주요 디자인 기준: 390px
- 태블릿 기준: 768px

## 12.2 요구사항

- 긴 코스명과 추천 이유가 잘리지 않는다.
- CTA 텍스트가 불필요하게 두 줄로 깨지지 않는다.
- 하단 고정 CTA 사용 시 브라우저 하단 영역과 겹치지 않는다.
- 데스크톱에서는 콘텐츠를 무리하게 넓히지 않는다.
- 추천 카드가 여러 개일 때 태블릿 이상에서 2열 배치를 고려할 수 있다.

# 13. 접근성 원칙

- 모든 버튼은 실제 `button` 요소를 사용한다.
- 링크 이동은 `a` 또는 라우터 Link를 사용한다.
- 선택형 버튼에는 `aria-pressed`를 적용한다.
- 키보드 Tab, Enter, Space로 핵심 흐름을 이용할 수 있어야 한다.
- `focus-visible` 스타일을 제거하지 않는다.
- 최소 터치 영역은 약 44×44px로 한다.
- 이미지에는 의미 있는 alt를 작성한다.
- 장식용 이미지는 빈 alt를 사용한다.
- 낮음, 보통, 높음 상태는 색상만으로 구분하지 않는다.
- 텍스트와 배경의 대비를 확보한다.
- 오류 메시지는 색상뿐 아니라 문장으로 전달한다.

# 15. Codex 구현 규칙

Codex는 작업 시 다음 규칙을 따른다.

1. 작업 전에 현재 저장소 구조와 기존 기술 스택을 확인한다.
2. 기존 프로젝트 구조와 코딩 스타일을 최대한 유지한다.
3. 불필요한 라이브러리를 추가하지 않는다.
4. 한 번에 모든 화면을 구현하지 않고 작은 단위로 작업한다.
5. 각 작업 후 lint, typecheck, test, build 중 저장소에서 가능한 검증을 실행한다.
6. 수정한 파일과 검증 결과를 정리한다.
7. 기획 문서에 없는 기능을 임의로 추가하지 않는다.
8. 실제 API가 없을 때는 service layer 아래에서 mock data를 사용한다.
9. 특정 코스 데이터와 문구를 UI 컴포넌트에 하드코딩하지 않는다.
10. 로딩, 빈 결과, 오류 상태를 정상 상태와 분리한다.
11. 모바일 반응형과 접근성을 작업 마지막이 아니라 구현 과정에서 함께 적용한다.
12. 디자인이 불명확할 때 임의로 새로운 패턴을 만들기보다 기존 컴포넌트 패턴을 재사용한다.
13. 큰 구조 변경이 필요하면 먼저 계획과 영향 범위를 설명한 뒤 수정한다.
14. 문서와 코드가 충돌하면 임의로 판단하지 않고 확인한다.

# 18. 최종 판단 기준

구현 결과를 평가할 때 가장 중요한 질문은 다음과 같다.

1. 첫 화면만 보고 길담이 어떤 서비스인지 이해되는가?
2. 조건 입력 과정이 여행 계획만큼 복잡하지 않은가?
3. 추천 결과에서 “차 없이 실제로 갈 수 있는가”를 바로 판단할 수 있는가?
4. 이동 피로도와 실제 수치가 감성 이미지보다 먼저 이해되는가?
5. 추천 이유가 납득 가능한가?
6. 결과가 없을 때 다음 행동을 안내하는가?
7. Tripadvisor를 참고했더라도 길담만의 문제 해결 방식이 드러나는가?
8. mock data를 실제 API로 바꾸기 쉬운 구조인가?
9. 모바일과 키보드 환경에서 핵심 기능을 사용할 수 있는가?
10. 기획에 없는 기능을 추가하느라 핵심 흐름이 흐려지지 않았는가?
