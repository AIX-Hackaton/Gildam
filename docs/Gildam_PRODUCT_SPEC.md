# 길담 Product Specification

> 이 문서는 Codex를 포함한 모든 개발 참여자가 길담의 기획 의도, MVP 범위, 화면 동작, 디자인 원칙을 동일하게 이해하기 위한 기준 문서다.  
> 구현 전에 이 문서를 먼저 읽고, 문서와 충돌하는 임의의 기능 추가나 해석은 하지 않는다.

---

## 0. 문서 사용 원칙

- 이 문서는 현재 MVP의 기준이다.
- 기획이 변경되면 코드보다 먼저 이 문서를 수정한다.
- 명시되지 않은 기능은 임의로 추가하지 않는다.
- 화면을 구현할 때는 기능뿐 아니라 문제 해결 의도와 사용자 경험을 함께 지킨다.
- 불명확한 부분은 추측해서 구현하지 말고 질문하거나 `TODO`로 남긴다.

---

# 1. 프로젝트 개요

## 1.1 프로젝트명

**길담**

### 서비스 한 문장

> 차 없이 전남을 다녀올 수 있을지를 먼저 판단하고, 그 하루를 지역 경험과 기록으로 연결하는 AI 문화관광 큐레이터

## 1.2 이름의 의미

‘길담’은 다음 두 가지 의미를 가진다.

- 지역의 길을 담는다.
- 여행자가 그곳에서 보낸 하루를 기록으로 남긴다.

MVP는 광주 출발 전남 당일치기 여행을 대상으로 하지만, 향후 다른 지역의 문화관광 데이터와 코스를 추가해 전국 단위 서비스로 확장할 수 있다.

## 1.3 프로젝트 목적

광주·전남에는 관광지, 지역 음식, 문화시설과 로컬 콘텐츠가 충분히 존재한다. 그러나 자가용이 없는 여행자는 관광 정보를 찾은 뒤에도 다음 내용을 직접 확인해야 한다.

- 광주에서 실제로 당일치기가 가능한가
- 대중교통 환승이 과도하지 않은가
- 도보 이동이 감당 가능한가
- 주어진 시간 안에 귀가할 수 있는가
- 코스 안에서 어떤 지역 음식과 문화를 경험할 수 있는가
- 여행 중 무엇을 관찰하고 기록하면 좋은가

길담은 흩어진 관광 정보와 이동 조건을 하나의 코스로 연결해, 사용자가 **실제로 떠날 수 있는 여행을 빠르게 선택하도록 돕는 것**을 목적으로 한다.

# 2. 문제 정의

## 2.1 핵심 문제

> 관광지가 부족한 것이 아니라, 자가용 없이 주어진 시간 안에 실제로 완주 가능한 여행인지 판단하기 어렵다.

기존 서비스에서는 관광지 정보, 길찾기, 일정, 후기와 여행 기록이 분리되어 있다. 사용자는 여러 서비스를 오가며 정보를 직접 비교하고 코스를 조립해야 한다.

## 2.2 해결하려는 사용자 불편

1. 갈 곳은 많지만 내 출발지와 시간에 맞는지 판단하기 어렵다.
2. 환승 횟수, 도보 시간, 총 이동시간과 귀가 가능성을 직접 계산해야 한다.
3. 관광지와 지역 음식을 하나의 동선으로 연결하기 어렵다.
4. 장소를 방문해도 무엇을 알고 보고, 무엇을 기록하면 좋은지 알기 어렵다.
5. 추천 결과를 본 뒤 다시 지도 앱에서 장소를 검색해야 한다.

## 2.3 해결하지 않는 문제

현재 MVP는 다음 문제를 해결하지 않는다.

- 전남 전체 지역의 실시간 자동 코스 생성
- 실시간 버스 지연과 막차 정보의 완전한 연동
- 숙소, 예약, 결제, 리뷰
- 맛집 순위와 사용자 평점
- 로그인과 개인 기록 보관
- 현재 위치 기반 실시간 재추천
- 전체 여행 사진 분석
- 여행 커뮤니티 기능

# 3. 목표 사용자

## 3.1 핵심 타겟

광주·전남을 잘 모르고, 자가용 없이 광주에서 전남 당일치기 여행을 떠나려는 20~30대 자유여행자

## 3.2 사용자 특성

- 광주송정역 또는 유스퀘어에서 출발한다.
- 혼자, 친구 또는 연인과 당일치기 여행을 떠난다.
- 여행 자체에는 관심이 있지만 계획 과정에는 피로를 느낀다.
- 모바일 지도와 SNS 사용에 익숙하다.
- 자연, 산책, 역사, 문화, 지역 음식과 사진 기록에 관심이 있다.
- 많은 선택지보다 적은 수의 신뢰할 수 있는 추천을 선호한다.
- 별도 앱 설치나 복잡한 입력 과정은 부담스럽게 느낀다.

## 3.3 대표 사용자 시나리오

유스퀘어에서 6시간 안에 다녀오려는 사용자가 역사·문화와 음식·시장 취향,
환승 최소 조건을 선택한다. 길담은 출발지·시간·이동 조건을 충족하지 못하는
코스를 제외하고 `NJ_LOW_01` 한옥고택 반걸음 코스를 1순위로 추천한다.

사용자는 다음 정보를 확인하고 여행 여부를 판단한다.

- 예상 소요시간
- 총 도보시간
- 환승 횟수
- 이동 피로도
- 추천 이유
- 지역 음식
- 주요 장소
- 로컬 포인트
- 오늘 담아볼 장면

이후 지도 앱을 통해 실제 길찾기로 이동한다.

# 4. 제품 목표와 성공 기준

## 4.1 제품 목표

### Goal 1. 계획 부담 감소

사용자가 여러 플랫폼을 오가지 않고 짧은 입력만으로 코스를 선택할 수 있어야 한다.

### Goal 2. 실행 가능성 판단 지원

추천 결과에서 도보, 환승, 소요시간과 이동 피로도가 먼저 보여야 한다.

### Goal 3. 추천 신뢰성 확보

검증된 코스 데이터 안에서만 추천하고 추천 이유를 설명해야 한다.

### Goal 4. 지역 경험 연결

관광지뿐 아니라 지역 음식과 로컬 포인트를 하나의 코스 안에서 제공해야 한다.

### Goal 5. 여행 기록으로의 확장

현재 구현 범위에서는 상세 화면에 ‘오늘 담아볼 장면’을 제공한다. 장면 카드 생성은 후속 범위다.

## 4.2 MVP 성공 기준

- 사용자가 조건 입력부터 추천 확인까지 2분 이내에 완료할 수 있다.
- 추천 결과에서 이동 피로도와 실제 이동 수치를 바로 확인할 수 있다.
- 정상 결과, 결과 없음, 로딩, 오류 상태가 모두 구현되어 있다.
- 320px 이상의 모바일 화면에서 가로 스크롤이 발생하지 않는다.
- 키보드만으로 핵심 흐름을 이용할 수 있다.
- 컴포넌트에 특정 코스 데이터가 하드코딩되어 있지 않다.
- 스프레드시트 스냅샷을 갱신해도 API·화면 구조를 크게 수정하지 않아야 한다.
- 추천 수치와 설명은 원천 시트의 안정 ID와 코드·API·화면 사용처까지 역추적할 수 있어야 한다.

# 5. 현재 MVP 구현 범위

## 5.1 필수 화면

1. 홈
2. 조건 입력
3. 추천 결과
4. 코스 상세
5. 결과 없음
6. 로딩 상태
7. 오류 상태

## 5.2 데이터 범위

- 출발지: 광주송정역, 유스퀘어
- 가능 시간: 6시간, 하루 종일
- 이동 부담:
  - 환승 최소
  - 이동 부담 낮게
  - 상관없음
- 취향:
  - 자연·산책
  - 역사·문화
  - 음식·시장
  - 감성기록
- 대상 지역:
  - 담양
  - 나주
  - 목포
- 주력 코스 수: 총 6개(모두 내부 시연용 관리 코스이며 현재 `publishable=FALSE`)
  - 담양·나주: 유스퀘어 출발
  - 목포: 광주송정역 출발
  - 지역별 이동 부담 완화형 1개와 일반형 1개
  - `LOW`라는 이름은 실제 피로도 등급이 낮다는 뜻으로 사용하지 않는다.

## 5.3 현재 단계에서 제외하는 화면

- 로그인
- 마이페이지
- 저장한 여행
- 전체 지도 탐색
- 사진 업로드
- 오늘의 장면 카드 생성
- 리뷰와 평점
- 예약과 결제
- 관리자 페이지

# 6. 핵심 사용자 흐름

## 6.1 정상 흐름

```text
홈
→ 여행 조건 입력
→ 추천 결과
→ 코스 상세
→ 외부 지도에서 장소 보기 또는 길찾기
```

## 6.2 결과 없음 흐름

```text
여행 조건 입력
→ 조건에 맞는 코스 없음
→ 결과 없음 안내
→ 조건 다시 설정
```

## 6.3 오류 흐름

```text
추천 요청
→ 데이터를 불러오지 못함
→ 오류 안내
→ 다시 시도
```

# 7. 화면별 요구사항

## 7.1 홈

### 목적

서비스의 핵심 가치를 짧게 전달하고 조건 입력으로 이동시킨다.

### 핵심 메시지

> 차 없이도 충분한 전남 당일치기 여행  
> 출발지와 시간, 취향을 선택하면 실제로 다녀올 수 있는 코스를 추천해드려요.

### 필수 요소

- 길담 로고 또는 서비스명
- 핵심 카피
- 짧은 설명
- 자동 재생 대표 이미지와 이미지별 제작자 출처
- `내 여행 조건 입력하기` CTA

### 동작

- CTA 선택 시 조건 입력 화면으로 이동한다.

### 완료 조건

- 첫 화면만 보고 서비스 목적을 이해할 수 있다.
- CTA가 가장 강한 시각적 위계를 가진다.
- 모바일 첫 화면에서 핵심 카피와 CTA를 확인할 수 있다.

---

## 7.2 조건 입력

### 목적

사용자가 최소한의 선택으로 추천 조건을 완성한다.

### 입력 항목

#### 출발지

단일 선택

- 광주송정역
- 유스퀘어

#### 가능 시간

단일 선택

- 6시간
- 하루 종일

#### 이동 부담

단일 선택, 기본값은 `상관없음`

- 환승 최소
- 이동 부담 낮게
- 상관없음

#### 취향

복수 선택

- 자연·산책
- 역사·문화
- 음식·시장
- 감성기록

#### AI 자연어 취향 입력

선택형 조건을 대체하지 않는 보조 입력이다. 사용자가 원하는 여행 분위기와 이동
방식을 문장으로 입력하면 AI가 이를 기존 `취향`과 `이동 부담` 코드로만 변환한다.

- AI는 코스를 생성하거나 추천 순위를 결정하지 않는다.
- 해석 결과는 기존 선택 UI에 반영하며 사용자가 다시 수정할 수 있다.
- 문장에 드러나지 않은 취향은 임의로 추정하지 않는다.
- AI 해석이 실패해도 수동 조건 선택과 추천 요청은 계속 사용할 수 있어야 한다.
- Gemini 인증키는 백엔드에서만 보관하고 프론트엔드에는 노출하지 않는다.

### 동작 규칙

- 출발지와 가능 시간은 하나만 선택할 수 있다.
- 이동 부담은 하나만 선택할 수 있으며 초기에는 `상관없음`을 선택한다.
- 취향은 한 개 이상 복수 선택할 수 있다.
- 출발지와 가능 시간이 완료되기 전까지 `코스 추천받기` 버튼을 비활성화한다.
- 출발지와 가능 시간만 선택하고 취향 없이 추천을 요청하면 이동하지 않고 하단에 `취향을 선택해주세요` 안내를 표시한다.
- 앱 내부에서 뒤로 갔다가 돌아오면 선택값을 유지한다.
- 페이지를 새로 열거나 새로고침하면 선택값을 초기화한다.
- 제출 중에는 중복 클릭을 방지한다.

### 상태

- 초기 상태
- 선택 상태
- 버튼 비활성화
- 버튼 활성화
- 제출 중 로딩

### 완료 조건

- 선택 여부가 색상만으로 구분되지 않는다.
- 체크 아이콘, 테두리 또는 텍스트 상태를 함께 사용한다.
- 버튼과 선택 항목은 키보드로 조작할 수 있다.

## 7.3 추천 결과

### 목적

사용자가 추천 코스를 빠르게 비교하고 추천 이유를 납득하도록 한다.

### 필수 요소

- 입력 조건 요약
- `조건 변경` 버튼
- 점수순 추천 코스 최대 3개
- 각 코스의 추천 순위 (`추천 1위`~`추천 3위`)
- 코스 카드

### 코스 카드에 포함할 정보

- 코스명
- 지역
- 대표 이미지
- 대표 이미지 제작자 출처
- 취향 태그
- 이동 피로도
- 예상 소요시간
- 총 도보시간
- 환승 횟수
- 귀가 상태 뱃지 (`FEASIBLE`은 `귀가 가능`, `TIGHT`은 `귀가 빠듯`)
- 귀가 교통 유형과 발권 방식에 따른 핵심 행동 안내
- 추천 이유 2~3개
- `추천 기준 보기`에서 취향 일치도·이동 부담·귀가 여유·지역성·기록 적합성의
  실제 적용 가중치 확인
- `코스 자세히 보기` 버튼

### 위계

1순위 추천 카드는 2~3순위 코스보다 시각적으로 명확하게 강조한다. 조건을
충족한 코스가 3개보다 적으면 존재하는 코스만 순서대로 표시하며, 순위를 채우기
위해 조건 미충족 코스를 포함하지 않는다.

### 상태

- 정상 결과
- 결과 1개
- 결과 여러 개
- 로딩
- 결과 없음
- 오류

### 완료 조건

- 카드 상단에서 이동 피로도와 이동 정보를 빠르게 확인할 수 있다.
- 추천 이유는 가중 점수가 높은 기준부터 1위 카드 3개, 2~3위 카드 2개를
  사용자용 문장으로 제공한다.
- 요약과 상세의 추천 이유는 장소·도보시간·귀가 여유 같은 같은 사실을 사용하고,
  보고서 표현을 피한 `~해요` 말투로 통일한다.
- 내부 점수 설명이나 상태 코드는 노출하지 않는다.
- 코스 선택 시 상세 화면으로 이동한다.

## 7.4 코스 상세

### 목적

사용자가 이 코스를 실제로 선택할지 최종 판단하도록 돕는다.

### 정보 순서

1. 대표 이미지와 이미지 내 제작자 출처, 코스명
2. 핵심 태그와 귀가 상태 뱃지
3. 이동 피로도
4. 예상 소요시간, 총 도보시간, 환승 횟수
5. 귀가 시간과 데이터 신뢰도
6. 추천 이유
7. 코스 순서
8. 지역 음식
9. 로컬 포인트
10. 오늘 담아볼 장면
11. 지도 보기 또는 길찾기 CTA

### 귀가 정보

- 귀가 가능 여부와 당일 재확인 필요 여부를 함께 표시한다.
- 기준 출발과 계획 귀가를 한 쌍으로 표시한다.
- 배차형은 출발 전 버스 도착정보 확인, 현장 발권형은 승차권 확보, 예약형은
  사전 예약을 안내한다. 사용자 문구에는 `BIS` 약어를 그대로 노출하지 않는다.
- 귀가 교통 기준은 배차형·계획 회차형·예약형을 구분해 표현하며 모든 유형을
  `막차`로 통합하지 않는다.
- 귀가 교통 안내는 `returnTransport.note`에서 한 문장만 표시한다.
- 코스 전체 출처와 내부 가공 데이터베이스는 귀가 정보의 출처로 표시하지 않는다.
  귀가 교통 전용 원천 출처가 구조화되기 전까지 출처 영역은 노출하지 않는다.
- 누락된 값은 임의로 추정하지 않고 해당 항목만 숨긴다.

### 코스 순서

타임라인 형태로 보여준다.

예시:

```text
유스퀘어 출발
→ 나주버스터미널
→ 금성관·목사내아
→ 나주곰탕거리
→ 나주버스터미널 귀가편
```

각 항목에는 필요에 따라 다음 정보를 표시한다.

- 장소명
- 장소 유형
- 머무는 시간
- 이동시간
- 짧은 설명

일정 유형은 `transport`를 `대중교통`, `walk`를 `도보`, `place`를 `장소`,
`food`를 `식사`로 표시한다.

### 오늘 담아볼 장면 예시

- 오래된 간판이나 골목의 색감
- 걷다가 발견한 풍경

### 지도 연결

- 지도 기능을 앱 안에서 직접 구현하지 않는다.

### 완료 조건

- 상세 컴포넌트 내부에 담양, 나주, 목포 데이터를 직접 하드코딩하지 않는다.
- 하단 CTA가 콘텐츠를 가리지 않는다.

# 8. 추천 및 데이터 원칙

## 8.1 추천 원칙

- AI가 새로운 코스를 자유롭게 생성하지 않는다.
- 사전에 등록되고 검증된 코스 DB 안에서만 추천한다.
- 시간 조건을 초과하는 코스는 먼저 제외한다.
- 이동 부담이 지나치게 큰 코스는 제외하거나 추천 순위를 낮춘다.
- 사용자에게 너무 많은 결과를 보여주지 않는다.
- 점수순 1순위 추천과 2~3순위 대안을 최대 3개까지 제공한다.

### 데모 검증 정책

- `GILDAM_EXPOSURE_MODE=INTERNAL`인 데모·내부 검토 환경에서는 토요일 운행,
  막차 시각, 이용일 교통편처럼 2차 확인이 필요한 항목을 추천 차단 조건으로 사용하지 않는다.
- 미확인 항목은 삭제하거나 확정값으로 바꾸지 않고, 코스 카드와 상세 화면에
  `2차 확인 필요` 안내와 이용 전 확인 항목으로 표시한다.
- 계획 소요시간이 사용자 가능 시간을 넘는 코스, 실제로 운행 불가가 확인된 코스,
  `BLOCKED` 코스는 데모 환경에서도 추천하지 않는다.
- `GILDAM_EXPOSURE_MODE=PUBLIC`에서는 `publishable=TRUE`인 코스만 노출한다.

## 8.2 이동 피로도

이동 피로도는 다음 값을 기준으로 계산한다.

- 총 도보시간
- 환승 횟수
- 왕복 포함 총 이동시간

초기 기준 예시:

| 항목 | 낮은 부담 | 중간 부담 | 높은 부담 |
|---|---|---|---|
| 총 도보시간 | 15분 이하 | 15~35분 | 35분 초과 |
| 환승 횟수 | 0회 | 1회 | 2회 이상 |
| 왕복 총 이동시간 | 90분 이하 | 90~180분 | 180분 초과 |

UI에서는 피로도 등급만 보여주지 않고 실제 수치도 함께 표시한다.

## 8.3 추천 이유 예시

UI에서는 각 추천 이유 앞에 원형 불릿 `•`를 표시하고, 문장 끝을 마침표로 통일한다.

- 자연·산책 취향과 주요 장소가 잘 맞아요.
- 환승이 1회로 비교적 단순해요.
- 코스 안에서 지역 음식을 경험할 수 있어요.
- 사진으로 남기기 좋은 골목과 자연 요소가 포함되어 있어요.

## 8.4 귀가 교통 데이터 원칙

- 교통 구간 탭의 코스별 마지막 구간을 귀가 교통의 정본으로 사용한다.
- 계산된 `returnFeasibility.status`가 `FEASIBLE`이면 `귀가 가능`, `TIGHT`이면
  `귀가 빠듯` 뱃지를 표시한다. `귀가 가능`은 연두색 배경·초록색 테두리와 텍스트,
  `귀가 빠듯`은 옅은 주황색 배경·주황색 테두리와 텍스트로 구분하며
  `NOT_FEASIBLE` 코스는 추천에서 제외한다.
- 귀가 교통은 `HEADWAY_SERVICE`, `SCHEDULED_SERVICE`,
  `RESERVATION_REQUIRED` 세 유형으로 보존한다.
- 배차형의 배차간격을 막차 시각으로 해석하지 않는다.
- 계획 회차·대체 회차·현장예매 조건은 자유 문구만이 아니라 구조화 필드로 저장한다.
- 예약형은 고정 시각을 만들지 않고 이용일 예매와 승차지 복귀 여유를 안내한다.
- 각 `returnTransport.segmentId`는 `교통 구간` 탭에 존재하는 안정 ID여야 한다.

## 8.5 Track #1 데이터 계보 원칙

- 주제개요서의 `A-DS01`~`A-DS19`를 원자료 레지스트리에 모두 등록한다.
- 기획서에 이름이 있다는 사실과 실제 사용 실적을 구분한다.
- `원본 레코드 키 → 시트 안정 ID → 코드 필드 → API 필드 → UI/계산` 경로가
  모두 있어야 `TRACEABLE_USED`로 표시한다.
- 증거가 없는 핵심 데이터는 `EVIDENCE_REQUIRED`, 후속 기능은 `DEFERRED`,
  MVP 밖은 `OUT_OF_SCOPE_MVP`로 표시한다.
- 지자체 BIS·시설 홈페이지·지도·예매처는 Track #1 데이터와 섞지 않고
  `SUPPLEMENTARY_SOURCE`로 관리한다.
- 데이터 사용현황은 `/api/meta/data-lineage`, 요약은 `/health.dataLineage`에서 확인한다.

# 9. 실데이터 스냅샷과 API 계약

## 9.1 개발 순서

Google Sheets를 정본으로 두고 `backend/app/courses/data.py`를 읽기 전용
schema v3.1 스냅샷으로 사용한다. 프론트엔드는 코스 데이터를 직접 import하지 않고

UI Component
→ Recommendation Service
→ FastAPI

## 9.3 구현 원칙

- UI 컴포넌트에서 특정 코스 데이터를 하드코딩하지 않는다.
- 데이터가 일부 누락되어도 화면 전체가 깨지지 않도록 처리한다.
- API 연결 함수는 별도 파일에서 관리한다.
- OpenAPI와 프론트엔드 타입의 필드 의미가 일치해야 한다.
- 코스 원천값은 UI 컴포넌트가 아니라 스냅샷·서비스 계층에서 관리한다.

## 9.4 AI 자연어 취향 해석 API

`POST /api/ai/interpret-preferences`는 사용자 문장을 다음 허용 코드로만 변환한다.

- `preferences`: `NATURE_WALK`, `HISTORY_CULTURE`, `FOOD_MARKET`, `MEMORY`
- `mobility`: `MIN_TRANSFER`, `LOW_BURDEN`, `ANY`

응답은 추천 요청의 입력을 돕는 용도로만 사용한다. 코스 DB, 시간·귀가 필터와 추천
점수 계산은 기존 규칙 기반 추천 엔진이 담당한다. AI 제공자 오류나 유효하지 않은
응답은 구조화된 API 오류로 반환하며 내부 오류 메시지와 인증키는 노출하지 않는다.

# 10. UX 원칙

## 10.1 핵심 원칙

### 선택을 줄인다

사용자는 여행 계획에 피로를 느끼는 사람이다. 자유 입력보다 명확한 버튼 선택을 우선한다.

### 기록은 여행 선택을 방해하지 않는다

‘오늘 담아볼 장면’은 서비스의 차별 요소지만, 코스 선택과 이동 정보보다 먼저 강조하지 않는다.

# 11. UI 및 비주얼 방향

## 11.1 레퍼런스 방향

Tripadvisor의 다음 특징을 참고한다.

- 둥근 카드
- pill 형태의 선택 버튼
- 명확한 CTA
- 큰 이미지와 간결한 정보 구성
- 친근하지만 과하게 장식적이지 않은 화면

단, Tripadvisor를 복제하지 않고 길담의 정보 구조와 브랜드에 맞게 재해석한다.

## 11.2 전체 분위기

- 정보는 명확하게
- 선택은 간단하게
- 기록 영역은 조금 더 감성적으로
- 브랜드명과 주요 제목에는 부리 계열 서체를 사용하고, 본문과 조작 요소에는 산세리프를 사용한다
- 관광 홍보물처럼 복잡하게 만들지 않는다
- 지나친 그라데이션과 장식은 피한다

## 11.3 형태

- 주요 카드와 버튼은 둥근 모서리를 사용한다.
- 선택 UI는 pill 또는 rounded button을 사용한다.
- 카드 안의 정보 계층을 명확히 구분한다.
- 한 화면에 너무 많은 카드와 태그를 배치하지 않는다.

## 11.4 문체

- 짧고 친절한 존댓말
- 과도한 감성 문구 금지
- 행정기관식 표현 최소화
- AI가 모든 것을 결정하는 것처럼 표현하지 않는다.

좋은 예:

- 내 조건에 맞는 코스를 찾았어요.
- 환승이 1회로 비교적 단순해요.
- 조건에 맞는 코스를 찾지 못했어요.

피해야 할 예:

- AI가 완벽한 여행을 설계해드려요.
- 당신만을 위한 환상적인 전남 여행
- 최적의 여행 경험을 선사합니다.

# 12. 반응형 원칙

## 12.1 기준

- 모바일 퍼스트
- 최소 지원 폭: 320px
- 주요 디자인 기준: 390px
- 태블릿 기준: 768px
- 데스크톱: 콘텐츠 최대 폭을 제한

## 12.2 요구사항

- 모바일에서 가로 스크롤이 발생하지 않는다.
- 긴 코스명과 추천 이유가 잘리지 않는다.
- CTA 텍스트가 불필요하게 두 줄로 깨지지 않는다.
- 하단 고정 CTA 사용 시 브라우저 하단 영역과 겹치지 않는다.
- 데스크톱에서는 콘텐츠를 무리하게 넓히지 않는다.
- 추천 카드가 여러 개일 때 태블릿 이상에서 2열 배치를 고려할 수 있다.

# 13. 접근성 원칙

- 모든 버튼은 실제 `button` 요소를 사용한다.
- 링크 이동은 `a` 또는 라우터 Link를 사용한다.
- 선택형 버튼에는 `aria-pressed`를 적용한다.
- 키보드 Tab, Enter, Space로 핵심 흐름을 이용할 수 있어야 한다.
- `focus-visible` 스타일을 제거하지 않는다.
- 최소 터치 영역은 약 44×44px로 한다.
- 이미지에는 의미 있는 alt를 작성한다.
- 제작자 정보가 있는 대표 이미지에는 오른쪽 아래 10px 위치에 12px 흰색 70%로
  `사진 제공 ({제작자}) - 한국관광공사`를 표시한다.
- 장식용 이미지는 빈 alt를 사용한다.
- 낮음, 보통, 높음 상태는 색상만으로 구분하지 않는다.
- 텍스트와 배경의 대비를 확보한다.
- 오류 메시지는 색상뿐 아니라 문장으로 전달한다.

# 15. Codex 구현 규칙

Codex는 작업 시 다음 규칙을 따른다.

1. 작업 전에 현재 저장소 구조와 기존 기술 스택을 확인한다.
2. 기존 프로젝트 구조와 코딩 스타일을 최대한 유지한다.
3. 불필요한 라이브러리를 추가하지 않는다.
4. 한 번에 모든 화면을 구현하지 않고 작은 단위로 작업한다.
5. 각 작업 후 lint, typecheck, test, build 중 저장소에서 가능한 검증을 실행한다.
6. 수정한 파일과 검증 결과를 정리한다.
7. 기획 문서에 없는 기능을 임의로 추가하지 않는다.
8. 프론트엔드는 service layer를 통해 실제 API를 호출한다.
9. 특정 코스 데이터와 문구를 UI 컴포넌트에 하드코딩하지 않는다.
10. 로딩, 빈 결과, 오류 상태를 정상 상태와 분리한다.
11. 모바일 반응형과 접근성을 작업 마지막이 아니라 구현 과정에서 함께 적용한다.
12. 디자인이 불명확할 때 임의로 새로운 패턴을 만들기보다 기존 컴포넌트 패턴을 재사용한다.
13. 큰 구조 변경이 필요하면 먼저 계획과 영향 범위를 설명한 뒤 수정한다.
14. 문서와 코드가 충돌하면 임의로 판단하지 않고 확인한다.

# 16. 구현 완료 체크리스트

## 사용자 흐름

- [ ] 홈에서 조건 입력으로 이동한다.
- [ ] 출발지와 시간은 단일 선택된다.
- [ ] 취향은 복수 선택된다.
- [ ] 자연어 취향 입력 결과를 기존 취향·이동 부담 선택으로 반영하고 다시 수정할 수 있다.
- [ ] 이동 부담은 단일 선택되며 추천 요청에 반영된다.
- [ ] 필수값이 없을 때 추천 버튼이 비활성화된다.
- [ ] 추천 결과에서 조건을 충족한 코스가 최대 3위까지 순서대로 구분된다.
- [ ] 코스 카드에서 이동 정보와 추천 이유를 확인할 수 있다.
- [ ] 결과 카드에서 귀가 교통 유형에 맞는 핵심 행동을 확인할 수 있다.
- [ ] 코스 상세에서 전체 일정과 지역 정보를 확인할 수 있다.
- [ ] 코스 상세에서 기준 일정과 귀가 교통 유형에 맞는 행동 안내를 확인할 수 있다.
- [ ] 지도 버튼이 올바른 외부 URL을 연다.
- [ ] 결과 없음에서 조건 입력으로 돌아갈 수 있다.
- [ ] 오류 화면에서 다시 시도할 수 있다.

- [ ] 실데이터 스냅샷과 UI가 분리되어 있다.
- [ ] 타입 정의가 공통으로 사용된다.
- [ ] 서비스 함수가 데이터 요청을 담당한다.
- [ ] 공통 컴포넌트가 재사용된다.
- [ ] 특정 코스 데이터가 컴포넌트에 하드코딩되어 있지 않다.

- [ ] 모든 귀가 교통 구간이 시트의 실제 `segmentId`를 참조한다.
- [ ] 사용 실적으로 표시한 데이터에는 원본 레코드 키와 소비처가 있다.

## 반응형

- [ ] 320px에서 가로 스크롤이 없다.
- [ ] 390px에서 주요 화면이 정상적으로 보인다.
- [ ] 768px 이상에서 레이아웃이 과도하게 늘어나지 않는다.
- [ ] 긴 제목과 설명이 잘리지 않는다.

## 접근성

- [ ] 이미지 alt가 작성되어 있다.
- [ ] focus-visible 상태가 보인다.
- [ ] 상태를 색상만으로 구분하지 않는다.
- [ ] 터치 영역이 충분하다.

## 검증

- [ ] lint가 통과한다.
- [ ] build가 통과한다.
- [ ] 대표 정상 흐름을 수동 테스트했다.

# 18. 최종 판단 기준

구현 결과를 평가할 때 가장 중요한 질문은 다음과 같다.

1. 첫 화면만 보고 길담이 어떤 서비스인지 이해되는가?
2. 조건 입력 과정이 여행 계획만큼 복잡하지 않은가?
3. 추천 결과에서 “차 없이 실제로 갈 수 있는가”를 바로 판단할 수 있는가?
4. 이동 피로도와 실제 수치가 감성 이미지보다 먼저 이해되는가?
5. 추천 이유가 납득 가능한가?
6. 결과가 없을 때 다음 행동을 안내하는가?
7. Tripadvisor를 참고했더라도 길담만의 문제 해결 방식이 드러나는가?
8. 스프레드시트 스냅샷을 갱신해도 API와 UI 계약이 유지되는가?
9. 모바일과 키보드 환경에서 핵심 기능을 사용할 수 있는가?
10. 기획에 없는 기능을 추가하느라 핵심 흐름이 흐려지지 않았는가?
