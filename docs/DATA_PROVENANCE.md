## 1. 최종 판단

현재 프로젝트의 코스·장소·교통 값은 지자체 BIS, 시설 공식 홈페이지, 지도,
예매처, 사용자 검증문서 등 **보조 공식 출처**를 기반으로 합니다. 그러나 초기
기획서에서 사용한다고 적은 Track #1 데이터에는 원본 레코드 키가 없습니다.

따라서 현재 증거로 말할 수 있는 범위는 다음과 같습니다.

- “스프레드시트와 보조 공식 출처로 6개 내부 시연 코스를 구축했다” → 설명 가능
- “A-DS01/A-DS11/A-DS13을 실제 제품 데이터로 사용했다” → 현재는 증명 불가
- “A-DS18을 현재 코스 장소 출처로 사용했다” → 사실 아님. 공식 CSV 범위 감사에만 사용
- “A-DS05 여행로그를 추천 점수에 사용했다” → 사실 아님. 의도적으로 제외
- “A-DS03/A-DS06으로 이미지·메뉴 OCR을 구현했다” → 사실 아님. 후속 범위

`/api/meta/data-lineage`의 현재 요약은 다음과 같습니다.

| 항목 | 현재 값 | 의미 |

### A-DS18 실제 대조 결과

- 공식 파일명: `전남광주통합특별시_지정 관광지 현황_20260618`
- 공개일·확인일: 2026-06-18 / 2026-08-19
- 원본: 35행, 2,734바이트, CP949 CSV
- SHA-256: `2ce74b739b8f3adab8695b536332d82bc75218055f6785d2e93fc71a981a913b`
- 이용조건: 공공저작물 출처표시 제1유형
- MVP 지역 필터 결과: `나주시|나주호|2000-03-22`,
  `담양군|담양호|1977-08-16`; 목포시 0행
- 현재 후보 장소·주력 코스 장소와 이름 직접 일치: 0건

즉 이 데이터는 “전남 관광지 전반” 목록이 아니라 법적으로 지정된 관광지·관광단지
35행입니다. 죽녹원·관방제림·금성관·목포근대역사관을 검증하는 범용 장소 DB로
사용하면 안 됩니다. 이번에는 **후보군 범위가 맞지 않다는 판단 근거**로만 사용했습니다.

`TRACEABLE_USED`는 아래 다섯 단계가 모두 이어질 때만 사용할 수 있습니다.

```text
A-DS 원본 레코드 키
→ 시트의 안정 ID(장소ID·구간ID·코스ID·후보ID)
→ data.py 스냅샷 필드
→ API 응답 또는 추천 계산
→ 실제 화면
```

## 3. 현재 실제 데이터의 사용처

Track #1 실적과 별도로, 현재 시트 데이터는 다음 경로로 실제 사용됩니다.

| 기능 | 시트의 안정 키 | 코드 | API | 화면/동작 |
|---|---|---|---|---|
| 추천 후보·노출 | `코스 요약[코스ID]`, `대체·보류 코스[코스ID]` | `schema.py`, `exposure.py`, 추천 필터 | 추천 `courses`, `exclusions` | 추천 결과·조건 변경 안내 |
| 귀가 가능성 | `교통 구간[구간ID]`, `코스 일정[코스ID]` | `feasibility.py` | `returnFeasibility` | 귀가 상태·2차 확인 안내 |
| 피로도 | `코스 요약[코스ID]`, `교통 구간[코스ID]` | `fatigue.py` | `fatigueExplanation` | 도보·환승·왕복교통 기여도 |
| 추천 순위 | 코스 취향·식사·로컬 설명 | 추천 점수 서비스 | `scoreBreakdown` | 추천 순서·요소별 근거 |
| 지역 경험 | `식사 후보[후보ID]`, `로컬 설명[장소ID]` | 상세 응답 조립 | `localFood`, `localPoints`, `scenePrompts` | 지역 음식·로컬 포인트·장면 |
| 길찾기 | 일정 장소의 좌표 | `kakao_map.py` | `routeLinks` | 구간별 카카오맵 링크 |
| 출처 표시 | 후보 장소·교통 구간·검증 링크의 URL·확인일 | `sources` | 상세 `sources` | 데이터 근거 카드 |

전체 기계 판독형 추적표는 다음 명령으로 확인합니다.
응답의 `sheetSnapshot.tabs`에는 현재 12개 탭의 GID와 행 번호 대신 사용할 안정 키가
함께 들어 있습니다.

```powershell
python -m backend.app.courses.lineage
Invoke-RestMethod http://127.0.0.1:8000/api/meta/data-lineage |
  ConvertTo-Json -Depth 12
```

## 4. 이번 감사에서 수정한 데이터 모델

### 4.1 귀가 교통을 세 유형으로 분리

기존 `lastReturnDeparture` 한 필드는 배차형·계획 회차형·예약형을 표현하지 못했습니다.
현재는 시트의 `시간종류`, `운영모델`, `값유형`을 다음 구조로 보존합니다.

| 코스 | 실제 시트 구간 | 구조 | 보존한 값 |
|---|---|---|---|
| DY_LOW_01 | DY_LOW_01-S2 | `HEADWAY_SERVICE` | 13:30 이후, 약 20분 배차, 당일 BIS 확인 |
| DY_NORMAL_01 | DY_LOW_01-S2 공유 | `HEADWAY_SERVICE` | 시트에 없는 S3를 만들지 않고 공유 구간 참조 |
| NJ_LOW_01 | NJ_LOW_01-S2 | `SCHEDULED_SERVICE` | 계획 13:05, 대체 13:35·13:50, 현장예매 |
| NJ_NORMAL_01 | NJ_NORMAL_01-S4 | `SCHEDULED_SERVICE` | 계획 16:35, 대체 17:20, 현장예매 |
| MP_LOW_01 | MP_LOW_01-S2 | `RESERVATION_REQUIRED` | 왕복 선예매, 13:30~14:30 후보창, 35분 전 복귀 |
| MP_NORMAL_02 | MP_NORMAL_02-S2 | `RESERVATION_REQUIRED` | 이용일 예매편, 40분 전 복귀 |
| MP_NORMAL_01 | MP_NORMAL_01-S4 | `RESERVATION_REQUIRED` | 보류 코스 귀가 구간; 노출 정책과 별도 보존 |

배차간격은 막차 시각이 아니며, 예약형에 절대 귀가 시각을 만들지 않습니다.
INTERNAL 데모에서는 2차 확인 안내를 붙이고 시간 산술상 가능한 코스를 보여줍니다.

### 4.2 추천 점수의 행 개수 편향 제거

이전 지역자원 점수는 `localFood + localPoints` 레코드 수에 비례했습니다. 같은
음식을 20행으로 나눈 코스가 한 행으로 묶은 코스보다 유리해질 수 있었습니다.
현재는 `지역 음식 존재`, `로컬 포인트 존재` 두 범주의 충족률과 검증상태만 사용합니다.

### 4.3 스키마와 계보 검증 강화

- API가 실제 소비하는 `verifiedDate`, `publishable`, `isPrimary`, 이미지,
  추천 이유, 설명, 왕복 교통시간, 목적지, 출처를 필수 필드로 검사
- 코스 ID·일정 ID 중복 검사
- 출처 URL·확인일 검사
- 귀가 교통 유형별 필수값 검사
- 모든 귀가 구간이 실제 시트 구간ID를 참조하는지 검사
- Track #1 19개 데이터셋의 누락·중복·허위 `TRACEABLE_USED` 표시 검사

## 5. 스프레드시트에 다음으로 추가할 구조

현재 요청은 시트 **점검**과 프로젝트 개선이므로 연결된 원본 시트는 수정하지
않았습니다. 다음 갱신 때 `데이터 계보` 탭을 추가하고 아래 컬럼을 사용해야 합니다.

| 컬럼 | 설명 |
|---|---|
| `lineageId` | 계보 레코드 고유 ID |
| `sourceDatasetId` | A-DS01 같은 Track #1 ID 또는 보조 출처 ID |
| `sourceRecordKey` | TourAPI contentId·원본 행 ID·AI-Hub 샘플 ID |
| `sourceSnapshotDate` | 원본 추출 기준일 |
| `sourceSnapshotHash` | 원본 파일/API 응답 SHA-256 |
| `sourceFieldsUsed` | 실제 사용한 원본 컬럼 |
| `sheetTab` | 반영된 탭 |
| `sheetRecordKey` | 행 번호가 아닌 장소ID·구간ID·코스ID·후보ID |
| `targetFields` | 정규화된 대상 필드 |
| `transformation` | `COPY`, `NORMALIZE`, `DERIVE`, `MANUAL_CURATE` |
| `algorithmVersion` | 파생·점수 계산 버전 |
| `usageStatus` | 실제 사용·증거 필요·보류·범위외 |
| `codeConsumers` | 계산·서비스 파일 |
| `apiFields` | 응답 필드 |
| `uiSurfaces` | 화면 위치 |
| `verifiedAt`, `verifiedBy` | 검수 시점·담당 |
| `license` | 재사용 조건 |

행 번호는 정렬할 때 바뀌므로 외래키로 사용하지 않습니다.

## 6. Track #1 데이터를 실제 사용으로 승격하는 순서

1. **A-DS13**: 백엔드 TourAPI 프록시로 현재 후보 장소마다 `contentId`, 사용 필드, 응답 스냅샷 해시를 기록합니다.
2. **A-DS18**: 현재 장소에는 억지로 연결하지 않습니다. 나주호·담양호를 실제 후보로
   채택할 때만 원본 행 키와 길담 `장소ID` 대응표를 만듭니다.
3. **A-DS01**: 로컬 포인트 한두 건부터 원문 키·원문 해시·요약문·검수자를 남깁니다.
4. **A-DS11**: 지역별 지표·기간·추출값과 담양·나주·목포 선정 논리를 표로 남깁니다.
5. **A-DS05**: 광주 출발 무차량 표본의 대표성이 확인될 때만 오프라인 추천 분석에 추가합니다.
6. A-DS03·A-DS06은 OCR·이미지 기능을 실제 구현할 때 승격합니다.

이 순서라면 데이터셋 수를 억지로 늘리지 않고도 “공공 관광정보로 장소를 검증하고,
AI-Hub 말뭉치로 설명을 보강하며, 통계는 지역 선정에 사용했다”는 연결 논리를
재현 가능한 증거와 함께 설명할 수 있습니다.

## 7. 발표 때 사용할 수 있는 정확한 설명

> 길담은 현재 Google Sheets의 7개 관리 코스와 지자체 BIS·공식 시설·지도·예매처
> 자료를 실제 추천과 화면에 사용합니다. Track #1의 19개 데이터는 모두 사용상태를
> 등록했지만, 원본 레코드 키가 없는 데이터는 사용 실적으로 과장하지 않았습니다.
> A-DS18은 공식 CSV를 대조해 현재 코스 장소와 직접 일치하지 않음을 확인했고,
> 다음으로 A-DS13 장소 대응표와 A-DS01의 설명 생성 근거를 연결하면,
> 원자료에서 추천 화면까지 전 구간을 역추적할 수 있습니다.

현재 “6개 검증 완료 코스”라고 표현하면 안 됩니다. 정확한 표현은
“주력 6개 내부 시연 코스 + 보류 1개, 공개 전 재검증 상태”입니다.
